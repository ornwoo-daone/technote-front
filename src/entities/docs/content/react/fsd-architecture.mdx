<Slide kick="문제 ①">
## 폴더를 "종류"로 나누면 생기는 일

대부분 이렇게 시작한다. 파일 종류별로 담는 방식이다.

```
src/
  components/   Button, DeckViewer, NotifyBell, SearchBox, CategoryCard …
  hooks/        useRead, useTheme, useSearch …
  utils/        docKey, formatDate, storage …
  pages/        Home, Category, Deck
```

처음 20개 파일까지는 잘 굴러간다. 문제는 **파일이 늘어날 때가 아니라, 기능을 지울 때** 드러난다.

<Warn>"알림 기능을 걷어내자"가 되면 `components/` `hooks/` `utils/` 세 군데를 뒤져야 한다.
무엇이 알림 전용이고 무엇이 공용인지 **폴더 구조가 알려주지 않는다.**</Warn>
</Slide>

## features 에 뭘 넣는가

가장 자주 헷갈리는 층이다. 기준은 하나다 — **동사로 이름이 나오는가.**

<div className="tscroll">

| 후보 | 이름이 이렇게 나온다 | 판정 |
|---|---|---|
| 검색창 | "검색<G>한다</G>" | <G>features/search/</G> |
| 테마 전환 | "테마를 바<G>꾼다</G>" | <G>features/theme/</G> |
| 읽음 추적 | "읽음을 기록<G>한다</G>" | <G>features/read-tracking/</G> |
| 문서 목록 데이터 | "문서<B>다</B>" — 명사 | <B>entities/docs/</B> |
| 버튼 스타일 | 행동이 아님 | <B>shared/ui/</B> |
| 덱 뷰어 | 행동이 아니라 화면 덩어리 | <B>widgets/</B> |

</div>

<Warn>**명사면 feature 가 아니다.** `features/user/` `features/docs/` 처럼 도메인 이름이 붙으면
그건 entity 다. feature 는 그 데이터로 사용자가 **무엇을 하는지**를 담는다.</Warn>
</Slide>

## 이 프로젝트의 배치

```
src/
  app/        App.tsx  main.tsx
  pages/      HomePage  CategoryPage  DeckPage
  widgets/    DeckViewer
  features/   search/  theme/  notify/  read-tracking/
  entities/   docs/ ─ registry.ts + content/*.mdx
  shared/     ui/slide-kit.tsx  assets/shell.css  types/mdx.d.ts
```

`HomePage` 가 조립만 한다는 게 실제로 이런 모양이다.

```tsx
// pages/HomePage.tsx — 데이터는 entities, 기능은 features 에서 가져다 쓴다
import { GROUPS, catsOfGroup, docsOf, docKey } from '../entities/docs/registry';
import { useReadList } from '../features/read-tracking/useRead';
import SearchBox from '../features/search/SearchBox';

const tilesOf = (g: GroupKey): Tile[] =>
  catsOfGroup(g).map((c) => {
    const docs = docsOf(c.f);
    return { ...c, count: docs.length, unread: docs.filter(...).length };
  });
```

<Note>`entities/docs/registry.ts` 는 어느 층에서든 import 한다. 셸 전체의 단일 소스라
**최하층처럼 취급**하기로 한 의도된 예외다.</Note>
</Slide>

<Slide kick="비교 ①">
## 기능별 폴더 (Bulletproof React) 와 뭐가 다른가

가장 널리 쓰이는 대안이다. 기능 단위로 폴더를 자르는 것까지는 같다.

```
src/features/
  awesome-feature/
    api/  components/  hooks/  stores/  types/  index.ts
```

<div className="tscroll">

| | Bulletproof React | FSD |
|---|---|---|
| 자르는 단위 | 기능(feature) 하나 | **층 × 슬라이스** 2차원 |
| 층 개념 | 없음 (features 와 그 외) | 6층 고정 |
| 도메인 데이터 위치 | 각 feature 안 | <span className="fsd-pick">entities 로 분리</span> |
| 기능 간 참조 | 관례로 금지, 강제는 없음 | 같은 층 참조 금지 |
| 학습 비용 | 낮음 | <B>높음</B> |

</div>

핵심 차이는 **entities 의 유무**다. 여러 기능이 같은 데이터를 쓸 때
Bulletproof 는 그 데이터가 어느 feature 소유인지 애매해지는데, FSD 는 아래층으로 내려 해결한다.

<Muted>이 프로젝트에서 `docs` 가 정확히 그 경우다 — 홈·카테고리·검색·알림 넷이 같은 레지스트리를 본다.</Muted>
</Slide>

## Atomic Design · Clean Architecture

<div className="tscroll">

| 아키텍처 | 나누는 축 | FSD 와의 관계 |
|---|---|---|
| **Atomic Design** | UI 크기 (atom→organism) | **직교한다.** 도메인 로직 배치엔 답을 안 준다. FSD 의 `shared/ui` 안에서 병행 가능 |
| **Clean / Hexagonal** | 도메인 ↔ 인프라 (안쪽이 바깥을 모름) | 발상이 같다. FSD 는 그걸 **프론트 폴더 규칙으로 단순화**한 판본 |
| **MVC / MVVM** | 표현 ↔ 로직 ↔ 데이터 | 층이 3개뿐. 기능이 늘면 각 층이 비대해짐 |
| **모듈 없음(타입별)** | 파일 종류 | 소규모에선 가장 빠름. 지우기가 어려워지는 게 한계 |

</div>

<Note>Atomic Design 은 **경쟁 관계가 아니다.** "버튼은 atom" 같은 UI 분류는
`shared/ui/` 내부 정리에 그대로 쓸 수 있다. 층 규칙과 충돌하지 않는다.</Note>
</Slide>

<Slide kick="단점" err>
## FSD 가 불편한 지점

솔직하게. 공짜가 아니다.

- **초반 오버헤드가 크다.** 파일 5개짜리 프로젝트에 6층은 과하다. 폴더가 코드보다 많아진다.
- **판단이 계속 필요하다.** "이건 widget 인가 feature 인가"에서 매번 멈춘다. 팀이면 합의 비용이 붙는다.
- **강제 수단이 없다.** 층 규칙을 어겨도 **빌드는 통과한다.** lint 규칙이나 grep 으로 따로 막아야 한다.
- **경로가 길어진다.** `../../entities/docs/registry` 같은 상대경로가 늘어난다. 별칭 설정이 사실상 필수가 된다.
- **공식 표준이 아니다.** 러시아권에서 시작해 문서·사례가 영어권 대안보다 적다. 검색으로 답 찾기가 상대적으로 어렵다.

<Warn>가장 흔한 실패는 **과잉 적용**이다. 슬라이스가 3개인데 층을 6개 만들면
구조가 도움이 아니라 세금이 된다. 층은 비워둬도 되지만, 억지로 채우면 안 된다.</Warn>
</Slide>

## 어떻게 관리할 것인가

**성장 순서를 미리 정해 두면 매번 고민하지 않아도 된다.**

<div className="tscroll">

| 시점 | 할 일 |
|---|---|
| 지금 | 6층 유지. `shared/lib` `shared/config` 는 **실제로 쓸 때** 만든다 |
| 슬라이스가 8개를 넘으면 | 각 슬라이스에 `index.ts` 를 두어 public API 를 명시 (내부 파일 직접 import 차단) |
| 상대경로가 3단계를 넘으면 | `@/` 별칭 도입 — Vite · webpack · tsconfig **세 곳**을 함께 고쳐야 한다 |
| 위반이 반복되면 | grep 대신 `eslint-plugin-boundaries` 로 강제 |
| 페이지가 5개를 넘으면 | `widgets` 층을 본격적으로 쓴다 (지금은 DeckViewer 하나뿐) |

</div>

<Note>**하지 말 것:** 새 층을 만드는 것. 6층 안에서 해결한다.
층을 추가하는 순간 "어느 층인가" 판단 비용이 급증한다.</Note>
</Slide>

## 한 장 요약

<div className="tscroll">

| 질문 | 답 |
|---|---|
| 규칙이 몇 개인가 | **하나.** 위층은 아래층만 import |
| features 에 뭘 넣나 | 이름이 **동사**로 나오는 것 |
| entities 에 뭘 넣나 | 이름이 **명사**로 나오는 것 (도메인 데이터) |
| 두 feature 가 서로 필요하면 | 경계를 잘못 그은 것 — 합치거나 아래로 내린다 |
| 잘 잡혔는지 어떻게 아나 | **"이 폴더 하나만 지우면 기능이 사라지는가"** |

<h1>DB2 SavingPlan<br/>코드 변경 & 데이터 플로우</h1>
<Lead>Oracle·Tibero에는 있는 **주기적 Plan 저장**이 DB2에는 없다. 무엇을 어디에 넣어야 하는지, 데이터가 어떤 경로로 흐르는지 정리한다.</Lead>
<Muted>기준 브랜치 `feature/db2-cachedplan` · 공용 코어 리팩터 `df31e9d8c` 반영</Muted>
</Slide>

<Slide kick="현재 상태">
## DB2만 주기 수집이 없다

|  | Oracle | Tibero | DB2 |
|---|---|---|---|
| 주기 Plan 저장 Task | <G>OraSavingPlan</G> | <G>TibSavingPlan</G> | <B>없음</B> |
| Plan 변경 감지 | <G>db_oracle_plan_change</G> | <G>db_tibero_plan_change</G> | <B>없음</B> |
| On-demand Plan | 있음 | 있음 | <G>plan / planCached / planFromActivity</G> |
| config 키 | `ora_plan_saving`=true | `tib_plan_saving`=false | <B>`db2_opt` 하나뿐</B> |

<Note>DB2는 **on-demand(사용자가 UI에서 누를 때)** 만 있다. 지나간 SQL의 plan은 남지 않는다.</Note>
</Slide>

## 대상 선정은 ActiveSessionList가 한다

```
// OraActiveSessionList.java:1636
if ((!username.equals("SYS")) && sql_hash_value != 0 && plan_hash_value != 0) {
    if (lastCallEt >= 5) {                    // 5초 이상 실행중인 세션만
        long savingMapValue = (long)sql_child_number << 32 | plan_hash_value;
        if (!savingPlanCheck.containsKey(savingMapValue) && savingPlan) {
            savingPlanCheck.put(savingMapValue, 0);   // 중복 방지
            savingPlanList.add(sp);                   // 큐에 적재
        }
    }
}
```

- **필터** — SYS 계정 제외 + `lastCallEt >= 5`(5초 이상 실행)
- **중복 방지** — `savingPlanCheck` HashMap, 하루 1회 clear
</Slide>

## Plan 변경 감지도 같은 자리

```
// OraActiveSessionList.java:1656 — 별도 클래스 없음. 인라인.
long planChangeKey = ((long)sql_child_number << 32) | sql_hash_value;
Long prev = planChangeCheckMap.get(planChangeKey);          // ExpiringMap 8h
if (prev != null && prev != plan_hash_value) {
    tc.category = "db_oracle_plan_change";
    tc.put("before_plan_hash_value", prev);
    tc.put("after_plan_hash_value", plan_hash_value);
    DataPackSender.send(tc);
    // 변경 전 plan / 변경 후 plan 을 둘 다 savingPlanList 에 넣는다
}
planChangeCheckMap.put(planChangeKey, plan_hash_value);
```

<Note>키는 **SQL**(`child_number|sql_hash_value`), 값은 **plan**(`plan_hash_value`). “같은 SQL인데 plan이 달라졌다”를 이 두 개의 분리로 판단한다.</Note>
</Slide>

<Slide kick="변경 ③">
## Db2SavingPlan — 신규 클래스

```
public class Db2SavingPlan implements IDBTask {
    public void init() { }                // reset 전용. 초기화는 생성자에서

    public void process(long t) {
        for (SavingPlan sp : drain(Db2ActiveSessionList.savingPlanList)) {
            PlanLists L = Db2Helper.planForSaving(sp.executableId);   // 신규 진입점
            if (L == null || L.id.size() == 0) continue;              // 빈 결과는 전송 안 함

            TagCountPack tc = new TagCountPack();   // 1 row = 1 pack
            tc.time = t;
            tc.category = "db_db2_plan_save";
            tc.putTag("oname", DbInfo.oname);
            tc.putTag("_no_5m_hour_", 0);
            tc.put("executable_id", sp.executableId);
            tc.put("id", L.id);  tc.put("parent_id", L.parent_id);  tc.put("depth", L.depth);
            tc.put("operator_type", L.operator_type);
            tc.put("cardinality", L.cardinality);  tc.put("total_cost", L.total_cost);
            tc.put("object_schema", L.object_schema);  tc.put("object_name", L.object_name);
            tc.put("source_type", L.source_type);
            DataPackSender.send(tc);
        }
    }
}
```
</Slide>

<Slide kick="DB2 난점 ①">
## EXPLAIN staging을 반드시 지워야 한다

<Warn>**실측(4.77, 2026-08-11):** 같은 SQL을 2번 EXPLAIN → EXPLAIN_STATEMENT 2→4행, EXPLAIN_OPERATOR 27→51행. **dedup도 덮어쓰기도 자동삭제도 없다.**</Warn>

- 현재 `Db2Helper` 전체에 **DELETE가 0건** — on-demand라 빈도가 낮아 지금은 버티는 것
- 주기 수집으로 바꾸면 **수집 주기 × 세션 수** 만큼 고객 DB에 행이 쌓인다
- 가득 차면 삭제가 아니라 **수집 중단**(PCTDEACTIVATE / SQL1630N) → 조용히 망가진다

<Muted>→ 읽은 직후 `EXPLAIN_TIME` 5-key 스코프로 STATEMENT / OPERATOR / STREAM DELETE. 보관은 와탭 서버가 한다.</Muted>
</Slide>

<Slide kick="DB2 난점 ②">
## plan_hash_value 에 해당하는 게 없다

|  | SQL 식별 | Plan 식별 | 변경 판단 |
|---|---|---|---|
| Oracle | sql_hash_value + child | <G>plan_hash_value</G> | <G>둘이 분리 → 정확</G> |
| DB2 | ? | <B>없음</B> | <B>불확실</B> |

- `executable_id` 는 **섹션 식별자**지 plan 해시가 아니다
- 재컴파일로 plan이 바뀌면 executable_id도 바뀌지만, **역은 보장되지 않는다** (캐시 evict 후 재적재 등)
- → executable_id 변경만으로 `db_db2_plan_change` 를 쏘면 **오탐** 위험

<Note>**미결정.** 1단계는 plan_save만, plan_change는 판단 근거를 따로 확보한 뒤 분리 진행하는 것을 권장.</Note>
</Slide>

<Slide kick="DB2 난점 ③">
## 버전 가드 — 10.5 미만은 불가

```
// Db2ActiveSessionList.java:1127
if ((versionMajor >= 10 && versionMinor >= 5) || versionMajor >= 11) {
    tc.put("uow_id", tc_uow_id);
    tc.put("activity_id", tc_activity_id);
```

- `EXECUTABLE_ID` 는 **11.x 쿼리에만** select 되어 있다 — 10.1 / 9.7 쿼리에는 없음
- SavingPlan은 같은 가드를 걸고, 미만 버전에서는 **Task 자체를 등록하지 않는** 편이 낫다
</Slide>

## 진행 순서 & 미결정

- **1단계** — Db2Helper 에 DELETE 추가 (지금 있는 누적 버그부터 해소, SavingPlan과 무관하게 이득)

- **4단계** — plan_change 는 판단 근거 확보 후 별도

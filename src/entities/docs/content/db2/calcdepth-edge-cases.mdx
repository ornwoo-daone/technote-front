## 종료 조건이 딱 하나뿐이다

```java
private static void calcDepth(Map<Integer, List<Integer>> tree,
                              int node, int depth,
                              Map<Integer, Integer> depthMap) {
    depthMap.put(node, depth);
    if (tree.containsKey(node)) {          // ← 유일한 브레이크: "자식이 없다"
        for (Integer child : tree.get(node)) {
            if (child != -1) {
                calcDepth(tree, child, depth + 1, depthMap);
            }
        }
    }
}
```

- **6행** 이 재귀가 멈추는 길은 단 하나 — `tree` 에 자식 목록이 **없는** 노드(잎)에 도달하는 것
- **4행** `depthMap.put` 은 "왔던 곳인지" 확인하지 않는다 — 기록일 뿐, **브레이크가 아니다**

<Warn>그런데 고리 안의 노드는 <b>전부 자식이 있다</b> (2의 자식 3, 3의 자식 2).
잎이 없는 길 = 종료 조건이 영원히 성립하지 않는 길. 코드가 잘못 도는 게 아니라, <b>설계된 유일한 출구가 이 데이터엔 존재하지 않는 것</b>이다.</Warn>
</Slide>

## 굴러떨어지는 과정 — 한 호출씩

tree = \{ 1→[2], 2→[3], 3→[2] \} 에서 `calcDepth(1, 0)` 을 부르면:

| 스텝 | 호출 | depthMap 상태 | 스택 깊이 |
|---|---|---|---|
| 1 | calcDepth(**1**, 0) | \{1=0\} | 1 |
| 2 | └ calcDepth(**2**, 1) | \{1=0, 2=1\} | 2 |
| 3 | &nbsp;&nbsp;└ calcDepth(**3**, 2) | \{1=0, 2=1, 3=2\} | 3 |
| 4 | &nbsp;&nbsp;&nbsp;&nbsp;└ calcDepth(**2**, 3) | \{1=0, <B>2=3</B>, 3=2\} | 4 |
| 5 | &nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;└ calcDepth(**3**, 4) | \{1=0, 2=3, <B>3=4</B>\} | 5 |
| 6 | … calcDepth(**2**, 5) | 2와 3만 계속 덮어씀 | 6 |
| ⋮ | ⋮ | depth 값만 무한히 커짐 | ⋮ |

- **스텝 4가 갈림길** — 3의 자식 2는 이미 다녀온 노드인데, 아무 검사가 없어 **그냥 다시 들어간다**
- depthMap은 키 2·3을 번갈아 **덮어쓸 뿐** 커지지 않는다 — 메모리로는 이상이 안 보인다
- 대신 **호출 스택**이 스텝마다 한 칸씩 쌓인다 — 이게 진짜 비용
</Slide>

## 자기참조 — 같은 원리의 한 줄짜리 버전

<Lead>고리에 노드가 두 개일 필요도 없다. **자기 자신이 자기 자식**인 행 하나면 충분하다.</Lead>

```java
// STREAM 행: source=2, target=2  →  tree: 2 → [2]

calcDepth(2, 1)
 └ calcDepth(2, 2)     // 2의 자식 = 2 자신
    └ calcDepth(2, 3)  // 또 자신
       └ …             // 다른 노드를 거칠 필요조차 없이 즉시 무한
```

- 순환 간선의 **최소형** — 원리는 동일, 속도는 더 빠르게 터진다
- 그래서 가드도 동일하게 먹힌다: "왔던 노드 재진입"이라는 공통 패턴 하나만 끊으면 둘 다 해결
</Slide>

<Slide kick="유입 경로">
## 이런 데이터가 실제로 올 수 있나

<Lead>정상 실행계획은 데이터가 스캔→RETURN 방향으로만 흐르는 **DAG라 고리가 없어야 한다.** 그런데 에이전트가 읽는 건 계획 그 자체가 아니라 **공유 staging 테이블의 행들**이다.</Lead>

| 경로 | 어떻게 고리가 되나 | 확도 |
|---|---|---|
| 재귀 SQL (`WITH ... UNION ALL`) | temp table이 자기 출력을 자기 입력으로 되먹임 — **4.77 실측: STREAM에 TEMP→TBSCAN→UNION→TEMP 순환 간선이 실제로 찍힘** (3→5→4→3) | <B>실측 확정 (2026-08-12)</B> |
| 동시 EXPLAIN 행 섞임 | 같은 EXPLAIN_STREAM 에 두 plan이 함께 써지고 5-key가 겹치면, 별개 트리 둘이 한 트리로 합쳐지며 우연히 고리 형성 | <W>저확률</W> |
| 손상·부분 적재·수동 조작 | 쓰다 만 행, 다른 툴의 간섭 | <W>저확률</W> |

<Warn><b>실측이 판을 바꿨다</b> — 재귀 CTE는 손상도 저확률 사고도 아닌 <b>평범한 SQL</b>(조직도·BOM·계층 조회)이다.
고객이 재귀 쿼리를 쓰고 그 plan을 조회하는 순간, 가드 없는 calcDepth는 <b>100% StackOverflowError</b>.
권한·설정과 무관 — EXPLAIN이 성공해도 돌아온 데이터 자체가 고리이기 때문.</Warn>

<Warn><b>프로덕션 발생 확인 (2.77 로그 수색, 2026-08-13)</b> — 가설이 아니라 이미 일어난 사고였다.
<br/>· <b>7/27 02:25–02:27</b> db2-metrics-extension 에이전트: DBX_PLAN(id 213) 요청 직후 <b>4건</b>
<br/>· <b>8/5 09:00–09:30</b> demo 에이전트: DBX_PLAN_HASH(id 224, planCached) 요청 직후 <b>7건</b>
<br/>스택트레이스 전부 <code>Db2Helper.calcDepth</code> 무한재귀. 원인 SQL도 특정 — 시연 부하 스크립트 4종(topsql 등)이
<code>WITH t(n) AS (... UNION ALL SELECT n+1 FROM t ...)</code> <b>재귀 CTE로 데모 테이블을 생성</b>하고,
그 쿼리의 plan을 UI에서 조회하는 순간 매번 터졌다. plan()·planCached() <b>두 경로 모두</b> 실발생.</Warn>
</Slide>

## 중복 간선 — 안 터지고 곱으로 일한다

<Lead>rank=1 필터는 화면용 `targetMap` 에만 걸린다. `tree` 에는 rank 2·3 행도 들어가서 같은 자식이 목록에 n번 실린다.</Lead>

```java
ctx.tree.computeIfAbsent(targetId, k -> new ArrayList<>()).add(sourceId);  // rank 검사 없음
...
for (Integer child : tree.get(node)) {   // [3, 3, 3] 이면
    calcDepth(tree, child, ...);         // 3의 서브트리를 통째로 3번 재계산
}
```

- 고리가 아니라 **잎은 있으니** 터지진 않는다 — 대신 층마다 중복이면 **곱으로** 불어난다 (2번씩 × 20층 ≈ 백만 순회)
- depth 값은 같은 걸 다시 쓰니 안 틀림 → 증상이 "가끔 plan 조회가 느림"뿐이라 추적이 가장 어려운 유형

<Warn><b>실측 확인 (2026-08-12)</b> — 이건 가설이 아니라 <b>에이전트의 평상시 동작</b>이다.
EXPLAIN 한 번에 EXPLAIN_STATEMENT 행이 2개(<code>EXPLAIN_LEVEL</code> = O 원문 / P 최적화) 생기는데 둘의 5-key가 동일해서,
3-way 수집 쿼리(<code>buildPlanSelectSql</code>)의 stt 조인에서 <b>모든 간선이 ×2로 곱해진다</b>.
4.77 실측: EXPLAIN PLAN 경로·EXPLAIN_FROM_SECTION 경로 <b>둘 다 5행 → 10행</b> —
즉 <b>planCached / planFromActivity 가 당하는 쪽</b>이고, 2-way 쿼리를 쓰는 plan() 은 무관.
수정 후보: <code>stt.EXPLAIN_LEVEL = 'P'</code> 필터 한 줄 (10행 → 5행 복원 검증됨).</Warn>
</Slide>

## 다중 뎁스 — 덮어쓰기가 운에 좌우된다

<Lead>공유 서브플랜(한 연산자의 출력을 두 연산자가 소비)이면 한 노드로 가는 길이 두 개가 된다. `depthMap.put` 은 검사 없이 덮어쓰므로 **마지막에 방문한 길**의 depth가 남는다.</Lead>

- 방문 순서 = tree 리스트 순서 = SELECT 행 순서인데, 최종 SELECT 에 **ORDER BY 가 없다** (`SELECT * FROM RankedRows`) → 행 순서 비결정
- 같은 plan을 두 번 조회해도 depth가 달라질 수 있고, 별개 규칙(마지막 행 승)으로 정해지는 `parent_id` 와 어긋난 조합이 서버로 갈 수 있다

<Muted>이 케이스의 상세 도식과 해법은 "calcDepth — tree DFS vs parentMap" 덱 참조</Muted>
</Slide>

## 고아 노드 — 조용한 행 밀림

<Lead>calcDepth는 루트 1에서만 출발한다. 1에서 안 닿는 행(다른 plan 잔여물·부분 적재)은 영영 방문되지 않아 depth가 없다.</Lead>

```java
Integer dep = ctx.depthMap.get(pi.id);
if (dep != null) L.depth.add(dep);   // depth 만 조용히 빠짐
L.id.add(pi.id);                     // id·parent_id 는 무조건 추가
```

- 터지는 것(순환)보다 발견이 늦다 — **화면만 슬쩍 이상해지는** 실패 모드

## 한 장 요약

| 케이스 | 왜 발생하나 | 기존 코드의 운명 |
|---|---|---|
| **순환·자기참조** | 유일한 종료 조건("잎 도달")이 고리 데이터엔 존재하지 않음 + 재방문 검사 부재 | <B>StackOverflowError</B> — catch(Exception) 관통 |
| 중복 간선 | rank 필터가 tree엔 미적용 → 같은 자식 n번 | 곱절 재계산 — 간헐적 느려짐 |
| 다중 뎁스 | put 덮어쓰기 + ORDER BY 없는 행 순서 | depth가 운에 좌우, parent_id와 어긋남 |
| 고아 노드 | 루트 1에서만 출발 → 끊긴 행은 미방문 | depth 리스트만 짧아져 조용한 행 밀림 |

<Note>넷의 공통 뿌리: <b>"데이터는 완벽한 트리"라는 검증 없는 가정</b> + 공유 staging 테이블 + 비결정 정렬.
무한재귀만은 가드 한 줄로 끊기지만, 나머지까지 근본적으로 없애려면 가정 자체를 줄여야 한다(→ parentMap 방식).</Note>

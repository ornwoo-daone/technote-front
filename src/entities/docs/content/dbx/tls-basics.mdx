## 없을 때 vs 있을 때 — Java 코드

**① TLS 없음 (WhaTap 에이전트 구간이 이 형태)**

```java
import java.net.Socket;
import java.net.InetSocketAddress;

Socket sock = new Socket();
sock.connect(new InetSocketAddress(host, 6600), timeout);
// 이게 전부다. 여기로 나가는 바이트는 그대로 네트워크에 실린다.
```

**② TLS 있음**

```java
import javax.net.ssl.*;

SSLSocketFactory factory = (SSLSocketFactory) SSLSocketFactory.getDefault();
SSLSocket sock = (SSLSocket) factory.createSocket(host, 443);

// 어떤 TLS 버전을 허용할지 명시
sock.setEnabledProtocols(new String[] { "TLSv1.3", "TLSv1.2" });

// 인증서의 이름이 접속한 호스트와 맞는지 검사하도록 켠다
SSLParameters p = sock.getSSLParameters();
p.setEndpointIdentificationAlgorithm("HTTPS");
sock.setSSLParameters(p);

sock.startHandshake();   // ← 여기서 인증서 검증·키 교환이 일어난다
```

<Warn>차이가 «옵션 하나»가 아니다. **클래스 자체가 다르다**(`Socket` vs `SSLSocket`).
그래서 코드에 `javax.net.ssl` import 가 없으면 TLS 가 아닌 게 확정된다.</Warn>

<Note>`setEndpointIdentificationAlgorithm("HTTPS")` 은 실무에서 자주 빠뜨리는 줄이다.
이게 없으면 **인증서는 검증하지만 «이 인증서가 이 서버 것인지»는 안 본다.**
유효한 남의 인증서로도 통과된다.</Note>
</Slide>

## SSL 과 TLS 는 뭐가 다른가

**같은 것의 옛 이름과 새 이름**이다. 기술이 다른 게 아니라 세대가 다르다.

<div className="tscroll">

| 이름 | 연도 | 상태 |
|---|---|---|
| SSL 1.0 | — | 공개된 적 없음 (설계 결함) |
| SSL 2.0 | 1995 | <B>폐기</B> |
| SSL 3.0 | 1996 | <B>폐기</B> — POODLE 취약점 |
| **TLS 1.0** | 1999 | <B>폐기</B> (2021 공식 종료) |
| **TLS 1.1** | 2006 | <B>폐기</B> |
| **TLS 1.2** | 2008 | <G>현역</G> — 가장 널리 쓰임 |
| **TLS 1.3** | 2018 | <G>권장</G> — 더 빠르고 안전 |

</div>

<Note>

이름이 바뀐 건 표준화 주체가 넷스케이프에서 **IETF**(국제 인터넷 표준화 기구)로
넘어가면서다. SSL 3.0 다음 버전이 TLS 1.0 이다.

**그런데 현장에서는 아직도 “SSL”이라고 부른다.** “SSL 인증서”, “SSL 적용” 같은 말은
거의 항상 실제로는 TLS 를 뜻한다. 라이브러리 이름도 `SSLSocket`, `SSLContext` 로 남아 있다.
그래서 코드에서 `SSL` 을 검색하면 TLS 사용 여부를 확인할 수 있다.

</Note>

<Warn>보안 점검에서 “SSL 을 쓰나요?”라고 물으면 “SSL 은 폐기됐고 TLS 1.2/1.3 을 씁니다”가
정답이다. 진짜 SSL 3.0 을 쓰고 있다면 그건 지적 사항이다.</Warn>
</Slide>

```java
// mTLS: 내 인증서(KeyManager) + 상대 검증용(TrustManager) 을 둘 다 설정한다
KeyManagerFactory kmf = KeyManagerFactory.getInstance("SunX509");
kmf.init(clientKeyStore, password);          // ← 내 신분증

TrustManagerFactory tmf = TrustManagerFactory.getInstance("SunX509");
tmf.init(trustStore);                        // ← 내가 믿는 CA 목록

SSLContext ctx = SSLContext.getInstance("TLSv1.3");
ctx.init(kmf.getKeyManagers(), tmf.getTrustManagers(), null);
SSLSocket sock = (SSLSocket) ctx.getSocketFactory().createSocket(host, port);
```

<Note>금융권·공공에서 자주 요구한다. 클라이언트마다 인증서를 발급·배포·갱신해야 하므로
**운영 부담이 크다.** 그래서 “mTLS 를 지원하나요?”는 가벼운 질문이 아니다.</Note>
</Slide>

<Slide kick="암호 기초 ①">
## 대칭키와 비대칭키

<div className="tscroll">

| | 대칭키 | 비대칭키 (공개키) |
|---|---|---|
| 키 | **하나** — 잠글 때와 열 때 같은 키 | **한 쌍** — 공개키로 잠그고 개인키로 연다 |
| 속도 | <G>빠름</G> | <B>느림</B> (수백 배) |
| 문제 | 키를 **어떻게 전달**하나 | 느려서 대량 데이터에 부적합 |
| 예 | **AES** | RSA, ECDSA |

</div>

<Flow steps={[
  {t:'비대칭키로', d:'대칭키를 안전하게 전달', accent:true},
  {t:'그다음부터', d:'빠른 대칭키로 실제 데이터'},
]} />

<Note>**TLS 는 둘 다 쓴다.** 핸드셰이크에서 비대칭키(느리지만 안전한 키 전달)로
대칭키를 합의하고, 실제 데이터는 대칭키(빠름)로 암호화한다.
각자의 장점만 취하는 구조다.</Note>

<Muted>WhaTap 에이전트 구간도 발상은 같다 — 액세스키에서 만든 «마스터키»로 «세션키»를 전달하고,
그 뒤로는 세션키를 쓴다. 다만 둘 다 대칭키(AES)이고, 서버 인증 절차가 없다는 점이 다르다.</Muted>
</Slide>

<Slide kick="암호 기초 ②">
## AES 는 무엇의 약자인가

**AES** = **A**dvanced **E**ncryption **S**tandard (고급 암호화 표준)

2001년 미국 표준 기관(NIST)이 공모를 통해 채택했다. 지금은 사실상 전 세계 표준이며,
**TLS 안에서 실제 데이터를 암호화하는 것도 대부분 AES** 다.

<div className="tscroll">

| 용어 | 풀이 |
|---|---|
| **블록 암호** | 데이터를 **16바이트씩** 잘라서 처리한다. 남는 부분은 채워야(padding) 한다 |
| **AES-128 / 192 / 256** | **키 길이**가 128·192·256비트라는 뜻. **블록 크기는 셋 다 16바이트로 같다** |
| **운영 모드** | 블록들을 **어떻게 이어 붙일지**의 규칙. ECB · CBC · GCM 등 |

</div>

<Warn>흔한 오해 — “AES-256 이면 블록이 32바이트”가 아니다. **키만 길어진다.**
키가 길수록 무차별 대입이 어려워지지만, **운영 모드를 잘못 고르면 키 길이는 의미가 없다.**</Warn>
</Slide>

<Slide kick="암호 기초 ③">
## 운영 모드 — 여기서 갈린다

같은 AES 라도 모드에 따라 안전성이 완전히 달라진다.

## 그래서 WhaTap 에이전트 구간은?

이제 앞 덱의 내용이 읽힌다.

<div className="tscroll">

| 질문 | 답 | 이 덱의 어느 개념인가 |
|---|---|---|
| TLS 쓰나? | 아니오 — `new Socket()` 뿐 | TLS 층이 빠진 상태 |
| TLS 버전은? | 해당 없음 | 협상 자체가 없으므로 |
| 인증서 관리는? | 대상 없음 | 인증서는 TLS 의 구성요소 |
| mTLS 는? | 없음 | 인증서가 없으므로 불가 |
| 그럼 암호화는? | 애플리케이션 계층에서 자체 처리 | 본문만 AES 또는 XOR |
| 어느 AES 모드? | **ECB** | 권장되지 않는 모드 |
| 무결성은? | 없음 | GCM 같은 인증 암호를 안 씀 |

</div>

<Warn>정리하면 — **«암호화는 한다. 다만 TLS 가 주는 세 가지 중 기밀성 일부만 있다.»**
기밀성·무결성·상대 인증이 모두 필요한 요건에는 망 계층 보호(전용선·IPsec VPN)를
함께 제안해야 하는 이유가 이것이다.</Warn>
</Slide>

<Slide kick="정리">
## 용어 한 장 요약

<div className="tscroll">

| 용어 | 풀이 | 한 줄 |
|---|---|---|
| **TLS** | Transport Layer Security | 연결을 통째로 보호하는 표준 층. 코드로 «켜야» 켜진다 |
| **SSL** | Secure Sockets Layer | TLS 의 옛 이름. 실제 SSL 버전은 전부 폐기 |
| **mTLS** | mutual TLS | 서버뿐 아니라 클라이언트도 인증서로 검증 |
| **CA** | Certificate Authority | 인증서에 서명해 주는 신뢰 기관 |
| **AES** | Advanced Encryption Standard | 표준 대칭키 블록 암호 |
| **ECB** | Electronic CodeBook | 블록 독립 암호화. 패턴 노출로 비권장 |
| **CBC** | Cipher Block Chaining | 앞 블록을 섞음 |
| **GCM** | Galois/Counter Mode | 암호화 + 무결성. 현재 권장 |
| **XOR** | exclusive or | 배타적 논리합. 단독으로는 암호가 아님 |
| **대칭키** | symmetric key | 같은 키로 잠그고 연다. 빠름 |
| **비대칭키** | asymmetric key | 공개키/개인키 쌍. 느리지만 키 전달에 안전 |
| **평문** | plaintext | 암호화하지 않은 원본 |

</div>

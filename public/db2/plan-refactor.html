DB2 · Plan 코드 리팩터

Plan 빌드 로직 공용화
· 스레드 안전 확보

세 plan 조회 경로가 같은 트리·depth 계산을 중복 구현했고, 하나는 static 가변 맵을 써 동시 호출 시 데이터가 섞일 수 있었다. 공용 코어로 통합해 중복 ~120줄 제거 + 스레드 안전 확보.

배경 · 도식

세 경로, 하나의 알고리즘

"가져오는 방법"만 다르고, 트리·depth·출력은 셋이 동일 → 공용화 대상.

문제 1

중복 구현

planCached는 메서드로 잘 분리돼 있었지만, 기존 plan()은 같은 로직을 인라인으로 재작성(적재 루프 + 출력 루프). 고칠 때 두 곳을 따로 손봐야 하는 구조였다.

문제 2 · 핵심

static 가변 맵 = 스레드 안전성 버그

// plan() 이 트리를 클래스 static 필드로 재사용
요청 A: tree[1] = [2]   // 넣는 중
요청 B: tree[1] = [9]   // 동시에 덮어씀 (같은 static tree)
→ A의 calcDepth가 B의 엣지까지 계산 → 엉뚱한 plan / NPE

동시 control 요청 시 데이터가 섞임. CLAUDE.md 리뷰 체크리스트 "static mutable" 위반.

해결

공용 코어 + 지역 컨텍스트

  • 행 적재를 collectRow(rs, ctx) 로 추출 → 3경로 공유
  • plan()을 지역 PlanContext + 공용 메서드로 교체 → static 필드 5개 제거
  • 인라인 SQL을 buildExplainSelectSql() 로 추출
  • 죽은 static 필드(planInfo) 제거
결과

−184 / +62, 스레드 안전

배운 점

공용화 ≠ static 공유

컴팩트함은 로직(메서드) 재사용에서 나오지, 데이터를 static으로 두는 데서 나오지 않는다. 상태는 호출 지역(PlanContext)으로 둬야 동시성 안전 + 자동 정리를 얻는다.

사이클 간 상태 유지가 필요한 델타 Task는 ExpiringMap instance 필드를 쓰지만, 한 호출로 끝나는 plan 조회는 지역 변수가 정답.

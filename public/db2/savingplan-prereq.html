SavingPlan에 필요한
DB2 지식

“Oracle처럼 주기적으로 plan을 저장한다”가 DB2에서 왜 그대로 안 되는지, 그 배경이 되는 DB2 고유 개념만 모았다.

구현 설계는 DBX · DB2 SavingPlan 구현 설계 참조

출발점

DB2에는 v$sql_plan이 없다

OracleDB2
plan을 읽는 방법v$sql_plan SELECT 한 방프로시저로 풀어낸 뒤 테이블에서 읽음
부작용없음 (읽기만)EXPLAIN 테이블에 행이 써짐
plan 해시plan_hash_value대응물 없음
이 세 줄이 DB2 SavingPlan 설계의 난점을 전부 만든다.
개념 ①

Section — 컴파일된 실행 코드

DB2는 SQL을 컴파일해 section이라는 실행 단위를 만들고, 이걸 package cache에 넣는다. 실행계획은 이 section 안에 들어 있다.

  • executable_id — 그 section을 가리키는 바이너리 식별자 (에이전트는 hex 문자열로 다룸)
  • plan을 보려면 “SQL 텍스트를 다시 EXPLAIN”이 아니라 “이 section을 풀어라” 라고 요청한다
  • 덕분에 실제로 돌아간 그 plan 을 얻는다 — 재EXPLAIN은 통계가 바뀌면 다른 plan이 나올 수 있음
// Db2Helper.java:309 — hex → bytes 로 넘긴다
cs.setBytes(1, hexToBytes(executableId));
개념 ②

Package Cache — 메모리, 그리고 evict

MON_GET_PKG_CACHE_STMT캐시에 살아있는 section 목록 + 통계
MON_GET_ACTIVITY지금 실행 중인 활동. executable_id 포함
  • package cache는 메모리다 → DB2가 LRU로 알아서 evict 한다 (자기제한적, 디스크 안 씀)
  • 즉 시간이 지나면 그 executable_id 로는 plan을 못 뽑는다
  • 이게 “주기적으로 미리 저장해 두자”(SavingPlan)의 존재 이유이자, 동시에 제약
evict 된 뒤 요청하면 EXPLAIN_FROM_SECTION 의 explain_time OUT이 NULL 로 온다 → 에이전트는 이걸 실패로 처리.
개념 ③

EXPLAIN_FROM_SECTION의 실제 동작

1. 호출executable_id 를 넘김
→
2. INSERTEXPLAIN_* 테이블에 plan을 써넣는다
→
3. OUT 5-key어디에 썼는지 좌표를 돌려줌
→
4. SELECT그 좌표로 다시 읽음
여기가 오해하기 쉬운 지점. 이름이 EXPLAIN_FROM_SECTION 이라 읽기 전용처럼 보이지만, 실제로는 staging 테이블에 쓰는 쓰기 작업이다. 그래서 정리 책임이 호출자에게 생긴다.
개념 ④

EXPLAIN_REQUESTER   // 누가 요청했나

  • 정리(DELETE)도 같은 5-key 스코프로 하면 내가 쓴 것만 정확히 지운다
호출마다 EXPLAIN_TIME 이 새로 생긴다 = 같은 SQL이어도 매번 새 행 세트가 쌓인다는 뜻.
개념 ⑤

EXPLAIN 테이블 3종의 역할

테이블담는 것에이전트가 쓰는 컬럼
EXPLAIN_STATEMENT문장 단위 헤더5-key (join 기준점)
EXPLAIN_OPERATOR연산자 노드OPERATOR_TYPE, TOTAL_COST
EXPLAIN_STREAM노드 사이의 흐름(간선)SOURCE_ID, TARGET_ID, STREAM_COUNT, 객체명
트리는 STREAM에서 나온다. DB2는 Oracle처럼 id / parent_id / depth 를 주지 않는다. SOURCE_ID → TARGET_ID 간선 목록을 받아 에이전트가 직접 트리를 만들고 depth를 계산한다.

계산 과정은 Plan depth 슬라이드 덱 참조

개념 ⑥

rank=1 — 간선 하나만 남기는 이유

ROW_NUMBER() OVER (PARTITION BY est.target_id
                   ORDER BY eop.total_cost DESC, est.STREAM_COUNT DESC) AS rank
// collectRow 는 rank == 1 인 행만 채택 (Db2Helper.java:429)
  • 한 target(부모 연산자)에 여러 stream이 붙을 수 있다
  • 그중 비용이 가장 큰 것 하나만 대표로 삼아 트리 노드를 만든다
  • → 화면에 그리는 plan 트리는 주 경로 중심의 요약이다

개념 ⑧

디스크에 쌓이는 것은 안 지워진다

자동 정리가득 차면
package cache (메모리)LRU evict알아서 밀어냄

event monitor는 임계 초과 시 오래된 걸 지우고 새로 담는 게 아니라, 비활성화되고 재활성화도 SQL1630N 으로 거부된다. “조용히 수집이 멈추는” 실패 모드.

실측 근거는 Plan 저장 disk 누적 이슈 문서 참조

개념 ⑨

스키마와 권한

  • EXPLAIN 테이블은 특정 스키마 아래에 존재한다 — 전역 시스템 뷰가 아니다
  • 없으면 SQL-204. 생성: CALL SYSPROC.SYSINSTALLOBJECTS('EXPLAIN','C',NULL,'<SCHEMA>')
  • 프로시저에 스키마를 NULL로 넘기면 SYSTOOLS 를 쓰려 해 권한 문제가 생김 → 에이전트는 db_user 스키마를 명시
  • 권한 부족은 SQL-551 / -552
// Db2Helper.java:306 — 명시적으로 넘겨 SYSTOOLS 의존 제거
String userSchema = Configure.getInstance().db_user.toUpperCase();
cs.setString(2, userSchema);
주기 수집이 되면 모니터링 계정 스키마에 EXPLAIN 테이블이 있는지가 설치 전제조건이 된다.
개념 ⑩

“plan이 바뀌었다”를 DB2는 알려주지 않는다

  • Oracle plan_hash_value = plan 모양의 해시 → 값이 다르면 plan이 다르다, 끝
  • DB2 executable_id = section 식별자 → plan이 바뀌면 대개 같이 바뀌지만, 그 역은 성립하지 않는다
  • 캐시에서 밀려났다 다시 컴파일되면 plan이 동일해도 다른 id 일 수 있다
따라서 executable_id 변화만으로 plan 변경을 판정하면 오탐이 난다. DB2에서 Oracle 수준의 plan-change를 하려면 plan 내용 자체를 비교하는 별도 근거가 필요하다.

정리

한 장 요약

  • plan은 section 안에 있고, section은 메모리 캐시에 있으며 evict 된다
  • plan을 보려면 프로시저로 staging 테이블에 써낸 뒤 5-key로 읽는다 → 쓰기 부작용
  • 디스크에 쌓인 건 DB2가 안 지운다. 가득 차면 수집이 멈춘다
  • 트리·depth는 에이전트가 계산한다 (STREAM 간선 → 트리)
  • plan 해시가 없어 변경 감지는 Oracle과 같은 방식으로 못 한다

DB2 SavingPlan
코드 변경 & 데이터 플로우

Oracle·Tibero에는 있는 주기적 Plan 저장이 DB2에는 없다. 무엇을 어디에 넣어야 하는지, 데이터가 어떤 경로로 흐르는지 정리한다.

기준 브랜치 feature/db2-cachedplan · 공용 코어 리팩터 df31e9d8c 반영

// OraActiveSessionList.java:1656 — 별도 클래스 없음. 인라인.

    tc.category = "db_oracle_plan_change";
    tc.put("before_plan_hash_value", prev);
    tc.put("after_plan_hash_value", plan_hash_value);

planChangeCheckMap.put(planChangeKey, plan_hash_value);
키는 SQL(child_number|sql_hash_value), 값은 plan(plan_hash_value). “같은 SQL인데 plan이 달라졌다”를 이 두 개의 분리로 판단한다.

변경 ③

Db2SavingPlan — 신규 클래스

public class Db2SavingPlan implements IDBTask {
    public void init() { }                // reset 전용. 초기화는 생성자에서

    public void process(long t) {
        for (SavingPlan sp : drain(Db2ActiveSessionList.savingPlanList)) {
            PlanLists L = Db2Helper.planForSaving(sp.executableId);   // 신규 진입점
            if (L == null || L.id.size() == 0) continue;              // 빈 결과는 전송 안 함

            TagCountPack tc = new TagCountPack();   // 1 row = 1 pack
            tc.time = t;
            tc.category = "db_db2_plan_save";
            tc.putTag("oname", DbInfo.oname);
            tc.putTag("_no_5m_hour_", 0);
            tc.put("executable_id", sp.executableId);
            tc.put("id", L.id);  tc.put("parent_id", L.parent_id);  tc.put("depth", L.depth);
            tc.put("operator_type", L.operator_type);
            tc.put("cardinality", L.cardinality);  tc.put("total_cost", L.total_cost);
            tc.put("object_schema", L.object_schema);  tc.put("object_name", L.object_name);
            tc.put("source_type", L.source_type);
            DataPackSender.send(tc);
        }
    }
}

DB2 난점 ①

EXPLAIN staging을 반드시 지워야 한다

실측(4.77, 2026-08-11): 같은 SQL을 2번 EXPLAIN → EXPLAIN_STATEMENT 2→4행, EXPLAIN_OPERATOR 27→51행. dedup도 덮어쓰기도 자동삭제도 없다.
  • 현재 Db2Helper 전체에 DELETE가 0건 — on-demand라 빈도가 낮아 지금은 버티는 것
  • 주기 수집으로 바꾸면 수집 주기 × 세션 수 만큼 고객 DB에 행이 쌓인다
  • 가득 차면 삭제가 아니라 수집 중단(PCTDEACTIVATE / SQL1630N) → 조용히 망가진다

→ 읽은 직후 EXPLAIN_TIME 5-key 스코프로 STATEMENT / OPERATOR / STREAM DELETE. 보관은 와탭 서버가 한다.

DB2 난점 ②

plan_hash_value 에 해당하는 게 없다

SQL 식별Plan 식별변경 판단
Oraclesql_hash_value + childplan_hash_value둘이 분리 → 정확
DB2?없음불확실
  • executable_id 는 섹션 식별자지 plan 해시가 아니다
  • 재컴파일로 plan이 바뀌면 executable_id도 바뀌지만, 역은 보장되지 않는다 (캐시 evict 후 재적재 등)
  • → executable_id 변경만으로 db_db2_plan_change 를 쏘면 오탐 위험
미결정. 1단계는 plan_save만, plan_change는 판단 근거를 따로 확보한 뒤 분리 진행하는 것을 권장.
DB2 난점 ③

버전 가드 — 10.5 미만은 불가

PostgreSQL · 인코딩

SQL_ASCII에서 한글이
조용히 깨지는 원리

SQL_ASCII는 "인코딩을 모른다는 선언" — 검증도 변환도 안 하는 유일한 타입. 그래서 섞인 인코딩이 에러 없이 통과해 깨진다.

바이트는 그대로, 해석에서 깨진다

구분

에러 나는 경우 vs 조용히 깨짐

케이스결과
선언 불일치 (EUC_KR 선언 + UTF-8 바이트)DB가 입력 거부(ERROR), 저장 안 됨
SQL_ASCII passthrough (EUC-KR 저장 + UTF-8 읽기)에러 없이 조용히 깨짐
  • 저장은 멀쩡, 읽는 시점 디코딩 불일치로 깨짐 (에러 없어 발견 늦음)
  • UTF-8 DB였다면 무효 바이트를 INSERT 단계에서 거부 → 애초에 안 들어감
  • set client_encoding은 "서버의 해석 규칙"만 바꿈 — 실제 전송 바이트는 안 바뀜
일반화

다른 DB의 유사 함정

  • Oracle: 클라 NLS_LANG == DB charset이면 변환 생략(pass-through), 특히 US7ASCII
  • MySQL: latin1이 전 바이트 수용 → 타 인코딩 유입 시 double-encoding
  • SQL Server: VARCHAR 코드페이지 불일치
근본 원인 공통: DB가 "저장된 바이트의 실제 인코딩"을 강제·보장하지 않을 때, 저장 인코딩 ≠ 읽는 쪽 가정 인코딩 불일치가 에러 없이 깨짐으로 드러남. SQL_ASCII는 그 무검증을 가장 노골적으로 하는 타입.
